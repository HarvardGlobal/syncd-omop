Patient journeys in the SYNCD database

What was built with PatientExploreR, TreatmentPatterns, CohortContrast and Comorbidity4j, what each showed about the 769 people with concurrent mental illness (MH) and substance use disorder (SUD), and how to read a patient journey.

What a patient journey is

A patient journey is the ordered sequence of clinically meaningful events for one person: diagnoses, screenings, treatments and visits, each with a date. In OMOP every event table carries a person_id and a date, so a journey is a person's rows across those tables, sorted by time. Journey analysis asks what happens, in what order, how long it lasts, and how that differs between groups.

Schematic of one concurrent-disorder journey. TreatmentPatterns would write this person's pathway as Sertraline → CBT+Sertraline → Sertraline → SUD counselling.

CohortThe group whose journeys you study, with an entry rule and an exit rule.
Index dateTime zero for each person. Here it is the day both disorders are present.
WindowHow far before and after the index date events count. A different window gives a different journey.
EraRepeated records of one treatment merged into a single period when the gaps are short.
CombinationTwo treatments overlapping long enough to count as one combined step.
ComparatorThe group you contrast against. "Enriched" always means compared with someone.

Four levels of journey analysis

Each tool answers a different question, from one person to the whole population. Together they cover the main ways people analyse journeys.

What was built

  • Shared study cohorts in results.cohort: concurrent MH and SUD (769), MH only (1,426), SUD only (979), plus five treatment cohorts. The counts match the simulation's ground truth exactly.
  • All four tools run against the local PostgreSQL database, each with a script in omop_tools/scripts/.
  • Compatibility fixes so tools written for older software run on this setup. They are listed in omop_tools/README.md; a separate patch file holds the PatientExploreR changes.
  • Checked in the browser: the PatientExploreR report and timeline, the TreatmentPatterns sunburst and Sankey, the CohortContrast viewer and the Comorbidity4j results page.

TreatmentPatterns

Core tool

OHDSI HADES R package · Rscript omop_tools/scripts/run_treatmentpatterns.R

Most people with concurrent disorders get treated for their mental illness only. One in ten gets treatment for both conditions, and 38% get no treatment at all.

MH treatment means sertraline or CBT. SUD treatment means counselling, naltrexone or buprenorphine-naloxone. Groups of fewer than 5 people are reported as 5, so the shares are approximate.

Worked well

  • Maintained OHDSI package that reads the standard cohort table.
  • Handles combinations and repeats, and keeps untreated patients as "None".
  • Sunburst and Sankey charts are easy to present.

Watch out for

  • Very sensitive to its settings. The defaults dropped every single-day CBT and counselling session until each session was given a 30-day episode.
  • The version available for R 4.3 crashes when one run has several target cohorts, so each cohort runs separately.

CohortContrast

Core tool

R package with a Python viewer · Rscript omop_tools/scripts/run_cohortcontrast.R · viewer at localhost:8050

Compared with age- and sex-matched people, the concurrent group is enriched for exactly what the simulation was built to produce: SUD diagnoses (9–20 times), counselling (29 times), MDD (10 times), sertraline (5 times), CBT (7 times) and PHQ-9 scoring (6 times). It also found two patient clusters, of 152 and 617 people.

Worked well

  • Data-driven. It finds the differences without being told which codes to look at.
  • The viewer adds timing (when after the index date an event occurs), concept overlap and patient clusters.
  • The two comparisons answer different questions: against MH-only patients it isolates what SUD adds; against matched controls it shows the whole profile.

Watch out for

  • New (version 1.0) and dependency-heavy. It needed newer R packages in a separate library and a Python viewer.
  • Results depend on the index date. Against MH-only patients, social-needs screening looks lower in the concurrent group, most likely because their window starts later and so covers fewer visits.
  • Matched controls have to be trimmed to their own observation periods first.

Comorbidity4j

Use for comorbidity figures

Java web app · omop_tools/scripts/c4j_start_server.sh, then c4j_export.sh and c4j_run_analysis.sh

Every MH × SUD pair co-occurs more than chance. The strongest are MDD with opioid use (odds ratio 5.0) and MDD with cannabis use (3.8); anxiety with alcohol use is the weakest (1.8). This matches the NSDUH odds ratio of 3.6 that the data was calibrated to.

Worked well

  • Fast (under a second) with standard statistics: relative risk, odds ratio, phi and adjusted Fisher tests.
  • Results split by sex, plus an interactive heatmap and network.

Watch out for

  • Diagnoses only, so not a journey tool. It cannot connect to the database; data goes in as exported files.
  • Only a web form and needs Java 8, so the run is scripted.
  • "Directional" mode counts only A-before-B and splits each pair in two. Leave it off when measuring comorbidity strength.

PatientExploreR

Demos only

R Shiny app · Rscript omop_tools/scripts/run_patientexplorer.R · localhost:8090

Good for showing one person's record: the patient report lists every event by type, and the timeline places visits in time. It is the most direct way to show an audience what a single journey looks like.

Worked well

  • No coding needed once it runs: search a patient, read the report, scroll the timeline.
  • A criteria search for finding every patient with a given concept is also included; it was not tested here.

Watch out for

  • Last updated in 2018 for MySQL and OMOP 5.3. It took six fixes to run on PostgreSQL and OMOP 5.4.
  • Single patients only. The timeline shows nothing until you pick visit types.
  • For long-term use, OHDSI ATLAS patient profiles or LinkR are better maintained.

Lessons for reading any journey analysis

  1. Define time zero first. The index date decides what counts as before and after. Here, anchoring on the second diagnosis put treatment for the first disorder before index, so the treatment window had to reach back 365 days.
  2. Settings change the story. Era-collapse gaps and minimum durations decide whether short treatments appear at all. Report them with the results.
  3. Always name the comparator. "Enriched" against MH-only patients and against the general population are different findings.
  4. Count the untreated. The "None" pathway was the largest group in every cohort, and it is often the most important finding.
  5. Order and co-occurrence are different questions. Comorbidity strength ignores order; directional analysis splits it. Choose deliberately.
  6. Synthetic data checks the pipeline, not the clinic. These results mostly recover the rules the data was built from: NSDUH rates, the 50/50 order of onset and the assumed treatment mix. That is the point of this dataset: when the same scripts run on real OMOP data, any difference reflects the data, not the tools.
Data note. All 10,000 patients are synthetic. Journey timing and treatment content are simulation assumptions, documented in the project README.
